# 导出表单：按阶段拆分填写内容

> 当前表单把 20 多个字段一次性铺给组员，**不区分项目处在哪个阶段**。
> 但一个 G0 立项的项目和一个 G3 结果验证的项目，需要填的东西几乎不重叠：
> G0 要的是「值不值得做」，G3 要的是「证明到了哪一步」。
>
> 本文设计**按阶段 + 按填写意图**拆分的表单。
>
> **状态：已实施**（2026-11-19）。四项待拍板事项按建议全部采纳，见 §9 实施记录。

---

## 0. 一个必须先说清的问题：现在的表单在"新建"时是不合格的

在讨论阶段拆分之前，我先查了表单实际产出的东西。有一个比阶段划分更基础的问题：

### 0.1 表单写出的 YAML 缺三个必需字段

`projectToYaml()` 产出：

```yaml
poc_id: POC-001
name: 人保财险SDL安全测试
org: {...}
...
```

**缺 `schema_version`、`gate_decisions`、`gate0.missing`、`gate0.complete`。**

实测：

```
has schema_version? false
has gate_decisions? false
has gate0.missing/complete? false false
```

后果：

| 缺失 | 后果 |
|---|---|
| `schema_version` | 台账按 **3.0 旧结构**处理这个文件（schema 文档明说「缺这个字段的文件按 3.0 旧结构处理」） |
| `gate0.missing` / `complete` | 派生字段缺失，CI 的 `derive --check` 会判定 stale 并拒绝 |
| `gate_decisions` | 升级审计轨迹整块消失 |

也就是说：**组员用新建表单填一个项目、下载 YAML、提交上去，CI 会报错。**
这不是阶段问题，是新建路径本身走不通。

> 不过要注意：表单当前的**真实交付路径不是 YAML**。`poc-export` skill 文档写的是
> 「下载 `poc-changes-<日期>.json`」，由 `poc-submit` 合并进现有 YAML。
> 但**代码下载的是 `.yaml`**（`toYaml()` + `text/yaml`）。
>
> 这是一个**文档与实现的真实分歧**，必须先裁决，因为它决定了下面所有设计的前提：
>
> - 若走 **YAML 直接替换**：表单必须写全所有字段，包括派生字段（不现实，派生值应由 `derive.mjs` 算）
> - 若走 **JSON 合并**（skill 文档的方案）：表单只交「变了的部分」，由 `poc-submit` 合并，
>   派生字段由 CI 重算 —— **这才是能工作的路径**
>
> 本文按**后者**设计：表单产出「变更集」，不是「完整文件」。

### 0.2 表单连 `outcome` 都表达不了

`FormProject` 接口里**没有 `outcome`**。而 `outcome` 是 G3/G4 的核心（证明了什么、
客户认可什么、下一步业务动作、Next Milestone）。当前表单对 G3/G4 项目**只能填进展**，
填不了结论——正好是最该填的那部分。

## 1. 核心设计：两个正交维度

组员填什么，由**两个独立问题**决定，不是一条轴：

```
维度 A：项目在哪个阶段   → 决定「哪些字段是主题」
维度 B：这次是什么意图   → 决定「是新建、补充、还是追加一条进展」
```

把它们合成一条「阶段表单」是不够的。同一个 G2 项目，两种场景完全不同：

| 场景 | 要填什么 |
|---|---|
| G2 项目**第一次**开测 | G2 前置条件、计划确认、第一条进展 |
| G2 项目**每周**同步 | 一条进展 + 下一步（其余全部只读） |

如果只按阶段拆，第二种场景会逼组员重新看一遍 20 个字段——这正是现在的问题。

### 1.1 维度 A：阶段决定"主题"

每个阶段有一个**主任务**，表单只把这个主任务做成可编辑，其余降级为只读上下文。

| 阶段 | 主任务 | 可编辑（主题） | 只读上下文 |
|---|---|---|---|
| **新建** | 立项登记 | 身份全部、`gate0` 五必填、`tech_owner` | — |
| **G0** | 值不值得做 | `gate0` 五必填、竞争对手、`gate0.review`（结论/评审人/日期） | 身份 |
| **G1** | 怎么赢 | `plan.criteria`(2–3)、`plan.scenarios`(3–5)、`risks`(≤3)、`our_edge`、`expected_recognition`、`timeline`、`gate1.conclusion` | 身份、gate0 |
| **G2** | 开测就绪 | `gate2.ready`、`gate2.prerequisites`、第一条进展 | 身份、gate0、plan |
| **G3** | 证明到什么程度 | 进展（含 `gate3_1`/`gate3_2`、evidence、customer）、场景/指标勾选 | 身份、gate0、plan |
| **G4** | 结论与转化 | `outcome` 全部、`business`（milestone/owner/deadline/status） | 全部 |

**这个映射不是我拍的，是从台账自己的结构推出来的**：

- schema 文档把字段分成 ①身份 ②gate0 ③plan ④progress ⑤outcome 五块
- 每个 gate 字段长在它对应的块里（`gate0.review` 在 ②，`gate1.conclusion` 在 ③，`gate3_1/2` 在 ④，`achievement` 在 ⑤）
- 16 条缺口规则也是按这个结构判定的（R1–R3 看 gate0，R4–R6 看 plan，R8–R10 看进展，R11 看 outcome）

所以「G1 填 plan、G3 填进展、G4 填 outcome」不是约定，是**数据结构本身**。

### 1.2 维度 B：意图决定"深度"

| 意图 | 触发方式 | 表单内容 | 输出 |
|---|---|---|---|
| **新建** | 不选项目直接导出 | 身份 + G0 五必填（最小可立项集） | 新文件 |
| **补充/完善** | 选一个项目 + 勾「补充信息」 | 当前阶段的主任务区（可编辑）+ 其余只读 | 变更集 |
| **追加进展** | 选一个项目 + 勾「记录进展」 | 只展开进展区（其余全部只读） | 追加一条 |

**「追加进展」是最高频的**，也是现在最该优化的：它应该只有一屏、五个字段。

## 2. 三种表单的实际形态

### 2.1 新建（立项登记）

只问**能立项的最小集合**：

```
身份（必填）：项目编号、项目名称、体系、客户公司、金额、类型、阶段、Owner、技术责任人
G0 五必填：why_customer、why_us、decision_chain、post_poc_decision、tech_owner
```

**刻意不做的**：不问 plan、不问 outcome。一个还没立项的项目，问它「成功指标是什么」
只会让人乱填，然后被 R3/R4 判成"计划不合格"。

这也是 R3 的设计意图：**G0 通过之后才要求 plan**。新建表单如果一上来就要 plan，
等于逼人在没想清楚之前写计划。

### 2.2 补充（当前阶段的主任务）

以 **G1** 为例：

```
┌─ 横幅：POC-001 · G1-方案设计 · 补充信息 ─────────────────┐
├─ 只读：身份摘要（折叠）                                   │
├─ 只读：Gate 0 五必填 5/5 ✓ 已通过（折叠，可展开看）        │
├─ 【可编辑】方案：痛点、期望认可、我方优势                  │
├─ 【可编辑】成功指标 2–3 条（带 id）                        │
├─ 【可编辑】验证场景 3–5 个（带 id）                        │
├─ 【可编辑】风险 ≤3                                        │
├─ 【可编辑】时间与结论：timeline、gate1.conclusion          │
└─ 就绪条：G1 完成度 · 还缺什么                              │
```

**已完成的阶段折叠成一行摘要**，不占版面。G1 项目不需要重新看 gate0 的五个大文本框。

### 2.3 追加进展（最高频）

这是唯一应该"一屏填完"的形态：

```
┌─ 横幅：POC-001 · G3-结果验证 · 记录进展 ──────────────────┐
├─ 日期 · 类型 · 这一次什么变了（三个必填，一行）             │
├─ 实际结果（一段话）                                       │
├─ 勾选：推进了哪些场景 / 验证了哪些指标（并排两列）          │
├─ 证据（标题 + 链接）                                      │
├─ 客户：同步对象 · 认可度 · 反馈                            │
├─ G3-1 / G3-2（仅 G3 阶段显示）                            │
└─ 下一步：目标 · 负责人 · 截止                              │
```

**其余全部只读**，一个字段都不重填。当前表单的进展区已经是这个样子了，
问题是它**和 plan、gate0、身份挤在同一页**，组员要滚三屏才能到它。

## 3. 只读上下文怎么处理

组员需要看到已有信息（否则不知道自己在补充什么），但**不需要重新编辑**。

三个层次，按重要性递减：

| 层次 | 呈现 | 例子 |
|---|---|---|
| **摘要行** | 一行文字 + 状态 | `Gate 0 · 五必填 5/5 · 评审通过 ✓` |
| **折叠块** | 点击展开，纯只读 | 五个 gate0 字段的原文 |
| **完全隐藏** | 不显示 | 与当前阶段无关的字段 |

**默认全部折叠**，只显示摘要行。理由：组员的注意力应该集中在**这次要填的东西**上，
其余是参考。全部铺开会把表单变回现在这个 20 字段的长页。

一个例外：**如果当前阶段的前置没满足**，那一块要自动展开并标红。
比如 G2 项目但 gate0 五必填还缺 2 项——组员必须看到这个，否则他填完 G2 的东西
提交上去，CI 还是会因为 R1 报错。

## 4. 阶段切换时的"跨阶段提醒"

有些字段虽然不属于当前阶段，但**一旦缺了会阻塞当前阶段**。表单必须主动提示：

| 当前阶段 | 会阻塞的前置 | 提示 |
|---|---|---|
| G1+ | gate0 五必填不全 | 「G0 还缺 N 项，评审前必须补齐」 |
| G2+ | `gate1.conclusion` 非通过 | 「G1 未通过，G2 开测会被 R7 判为未就绪」 |
| G3+ | `gate2.ready` 非 Ready | 同上 |
| G4 | 最新进展 `gate3_2` 非已确认 | 「G3 未确认，G4 结论无法成立」 |

这是就绪条的扩展：**从"本阶段缺什么"扩展到"本阶段被什么卡住"**。

## 5. 导出入口要改

现在的导出对话框只有一个项目列表 + 全选/全不选：

```
☑ POC-001 人保财险SDL安全测试
☑ POC-006 人保财险全国信创...
[全选] [全不选]          已选 30 个
```

**问题**：选 30 个项目会生成一个 30 个项目的表单，组员打开后要用下拉框切换——
这正是 PR #16 那个「1498 行全量」问题的表单版本。

需要改成两级：

```
① 这次要做什么？
   ○ 新建项目（不选任何项目）
   ○ 补充信息（选项目）
   ○ 记录进展（选项目）

② 选哪些项目？
   [按阶段筛选] G0 30 · G1 0 · G2 0 · G3 0 · G4 0
   ☑ POC-001 ...
```

**按阶段筛选**是关键：批量给「所有 G0 项目」发补充表单，和给「所有项目」发，
是完全不同的两件事。

## 7.1 原始议题（存档）

### 原 ① 输出格式：YAML 还是 JSON？

### ① 输出格式：YAML 还是 JSON？

这是最基础的一条，其他都依赖它。

| 选项 | 表单输出 | 合并方式 | 派生字段 |
|---|---|---|---|
| **A. JSON 变更集**（skill 文档的方案） | `poc-changes-*.json`，只含变了的部分 | `poc-submit` 合并 | CI 重算 ✓ |
| B. YAML 完整文件 | 完整 `*.yaml` | 直接替换 | 表单得自己写，且会和 CI 冲突 ✗ |

**我建议 A**，理由：派生字段（`gate0.missing`/`complete`、`priority`、场景状态）
必须由 `derive.mjs` 算，表单写不了也不该写。B 方案要么漏写派生字段（CI 报错），
要么硬编码一套计算逻辑（必然和 CI 漂移）。

但现在**代码是 B、文档是 A**。这个分歧不裁决，P0 就没法做。

### ② 新建表单要不要问 plan？

我建议**不问**。理由：R3 的设计是「G0 通过后才要求计划」，新建时问 plan
等于逼人在没想清楚前写计划，然后被 R4/R5 判不合格。

但反方观点：plan 的信息（客户痛点、期望认可）在立项时其实已经知道，
早填能减少一次往返。

### ③ 「补充」是只改本阶段，还是允许改任何阶段？

| 选项 | 行为 |
|---|---|
| **A. 只改本阶段** | G1 项目的表单只能改 plan，gate0 只读 |
| B. 允许改任何 | 全部可编辑，只是默认折叠 |

**我建议 A**：阶段是有序的，改上游阶段意味着结论变了，那应该走「Gate 回退」而不是
悄悄改字段。但 A 的代价是：发现 gate0 写错了，得单独发一个 G0 表单。

### ④ 批量导出要不要按阶段拆分？

给 30 个 G0 项目发一份表单，还是给每个项目单独一份？

| 选项 | 行为 |
|---|---|
| **A. 一个阶段一份** | 30 个 G0 项目 → 一份表单，下拉切换 |
| B. 每个项目一份 | 30 个文件 |

**我建议 A**：组员通常负责一个阶段的一批项目。但 A 要解决「一份表单里 30 个项目」
的导航问题——现在的下拉框不够。

## 8. 一个必须承认的现实

**这套设计在 G0 阶段是完整可用的，G1–G4 是纸面设计。**

真实台账 30/30 全在 G0，`plan` 和 `outcome` 全空。这意味着：

- G1 表单（填 plan）**没有真实数据能验证**
- G3 表单（gate3_1/2）**没有真实数据能验证**
- G4 表单（outcome）**连 FormProject 都没有这些字段**

所以实施顺序上，P1 只能先做**新建 + G0 补充 + 进展**这三块，
G1–G4 的形态要先有项目走到那个阶段才能验证。

这跟提醒设计（[DESIGN-提醒与Gate评审.md](DESIGN-提醒与Gate评审.md)）面对的是同一个现实：
**设计可以先行，验证必须等数据。**

## 9. 实施记录（2026-11-19）

### 9.1 移除「3.0 旧结构」兼容逻辑

这条逻辑**从未真正实现过**：`schemas/poc-schema.md` 写着「缺 `schema_version` 的文件按 3.0
旧结构处理」，但台账校验器一直直接拒绝：

```
tools/validate.mjs:92  if (text(raw.schema_version) !== '3.1') → E-VERSION
```

所以这次改动**没有改变任何实际行为**，只是让文档与实现对齐：

| 位置 | 改动 |
|---|---|
| `src/types.ts` | 删掉「按 v3.0 降级处理」的注释，改为说明「没有 v3.0 兼容模式」 |
| `src/form.ts` | 兼容门措辞改为「台账不做旧结构兼容」 |

表单侧的兼容门**保留**：它是防旧表单被静默半导入，与「旧台账文件兼容」是两件事。

### 9.2 已实现

| 项 | 实现 |
|---|---|
| 意图三选一 | `FormIntent = 'new' \| 'supplement' \| 'progress'`，贯穿 transport / api / dialog |
| 阶段决定主题 | `SECTIONS_FOR_STAGE`（G0→identity+gate0，G1→plan+gate12，G3→progress，G4→progress+outcome） |
| 只读上下文 | `contextGate0` / `contextPlan` / `contextIdentity` 摘要块 |
| 更晚阶段不显示 | 按 `order.indexOf` 截断，G1 看不到 outcome |
| JSON 变更集 | `projectToChangeSet` / `buildChangeDocument` / `toChangeDocument()` |
| 去掉派生字段 | 变更集不写 `gate0.missing`/`complete`、`priority`、`gate_decisions` |
| 补 `schema_version` | 变更集带 `schema_version: "3.1"` |
| G4 结论块 | `FormProject.outcome` 新增 11 个字段 + `outcomeCard()` |
| 导出入口 | 意图按钮 + 阶段筛选（带计数，0 个的阶段置灰） |

### 9.3 实施中发现并修掉的两个设计缺陷

**① `outcome` 曾作为 G1 的只读上下文出现。** 测试断言「G1 不该看到 outcome」时失败：
`resolveSections` 把所有非可编辑区块都算作 context，包括**还没发生的后续阶段**。
展示一个空的 G4 结论块给正在填 G1 的人，等于邀请他编一个结论。
已改为只取 `order.indexOf < currentIndex` 的前置区块。

**② 新建表单显示了「方案 · 只读」和「计划聚焦」。** 新建时本来就没有计划（R3 的设计是
G0 通过后才要求计划），展示「0 条指标，要求 2–3」是在**凭空制造一个失败**。
已按 `intent === 'new'` 隐藏这两处。

### 9.4 验证
