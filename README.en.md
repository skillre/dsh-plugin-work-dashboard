## Install

After development and test cleanup, **the user** chooses the source and confirms installation in the DSH Desktop Client or Web UI **Plugins** manager. After publication and verification of the target manager, offer the npm package spec `@skillre/dsh-plugin-work-dashboard@<version>`. Before publication, an absolute path to a built local package directory or `.tgz` can be offered only if this manager accepts it and the artifact is installable. Offer a GitHub repository URL only after verifying the manager supports it and the repo ships a safe, documented, self-contained `prepare` build. The developer/agent must not preinstall a plugin into the user's profile.

Local development verification (**owned, disposable, non-Desktop profile and packed tarball only**):

```sh
npm install
npm run check
npm pack
dsh plugin --profile <dev-profile> add ./skillre-dsh-plugin-<slug>-<version>.tgz
dsh --profile <dev-profile> --dump-config
```

These commands are **temporary tests only**. Perform a bounded startup, then stop the process and uninstall the test bundle or clean up only the confirmed owned isolated profile even if the test fails; check that dependency, selection and config changes are gone. Testing in the user's real Desktop/Web profile requires prior consent and a baseline inventory, followed by removal of only test-created state; never delete preexisting installations or data. Never use `dsh plugin ... add .`: a source link hides plugin/host API drift. A `file:` manifest dependency is not the same as a local package address entered in the user-facing manager.

## Display metadata

DSH reads a plugin card **without activating the plugin**, so these resources must ship inside the package:

- `locale/en.json` (required) and `locale/<lang>.json`, shaped as `{"meta": {"title": "...", "description": "..."}}`.
  They are resolved through the Node ESM resolver, so `exports` must declare `"./locale/*.json"`; without that
  entry the resolver throws `ERR_PACKAGE_PATH_NOT_EXPORTED`, DSH **swallows the failure silently**, and the card
  degrades to the bare package name with no diagnostic anywhere.
- `icon`: a top-level field naming an in-package relative SVG/PNG/JPEG/WebP file of at most 256 KiB; `files` must cover it.

`package.json#dsh.manifestVersion` is `1`. `engines.dsh` states the DSH lines this package was really mounted and tested against: a range is documentation, not evidence.

The generated `meta.title` uses the plugin slug as a placeholder and **must be replaced with the real product name before release**; the description likewise. The icon is fleet placeholder artwork and should be replaced with the plugin's own mark.

## Compatibility

| DSH version | Result | Verified | Notes |
|---|---|---|---|
| 0.2.2-rc.1 | Project shell only; no business compatibility claim | 2026-11-05 | A real mount test is required before release |

Machine-readable evidence belongs in `compatibility.json`. Before release, add at least one real record:

```json
{
  "dsh": "<exact-version>",
  "verifiedAt": "YYYY-MM-DD",
  "result": "passed",
  "checks": ["dump-config", "bounded-startup"]
}
```

A Client package must also record `desktop-client-ui` or `web-ui` in `checks` for the target actually tested (both only if both were checked); a standalone browser pass does not prove the Electron Client works. A peer range is not compatibility evidence. After recording evidence, rebuild and mount the exact final tarball so the tested artifact also contains that evidence.
