# 导出 POC 收集表单（v3）

生成一个**自包含 HTML** 文件：组员双击就能填，无需服务器、无需联网、无需 GitHub 账号。

## 怎么生成

用随本 skill 发布的脚本，不要去找外部脚本（旧版的 `~/dsh-test/poc_form.py` 是 v1 生成器，
产出的 YAML 台账已经读不了）：

```sh
# 补全模式 + 补充信息意图（最常用：给已有项目补齐当前阶段）
node <skill-dir>/scripts/export-form.mjs \
  --mode fill --intent supplement \
  --poc ~/.dsh/cache/work-dashboard/repo/projects/POC-006.yaml \
  --out /tmp/表单-POC-006.html

# 记录进展：只展开「这一轮进展 + 下一步」，一屏
node <skill-dir>/scripts/export-form.mjs \
  --mode fill --intent progress \
  --poc ~/.dsh/cache/work-dashboard/repo/projects/POC-006.yaml \
  --out /tmp/表单-POC-006-进展.html

# 批量：多个项目打包成一个表单
node <skill-dir>/scripts/export-form.mjs \
  --mode fill --intent supplement \
  --poc "~/.dsh/cache/work-dashboard/repo/projects/*.yaml" \
  --out /tmp/表单-批量.html

# 新建模式：从零建一个新项目（不需要 --poc）
node <skill-dir>/scripts/export-form.mjs --mode new --intent new --out /tmp/表单-新建.html
```

`<skill-dir>` 就是本 skill 所在目录（`skills/poc-export/`），模型可通过
`resourceBase` 解析相对路径。脚本只读 YAML、只写 HTML，不改台账。

### 参数

| 参数 | 取值 | 默认 | 说明 |
|---|---|---|---|
| `--mode` | `fill` / `new` | `fill` | `fill` 从台账读项目；`new` 生成空白项目 |
| `--intent` | `new` / `supplement` / `progress` | `mode=new` → `new`；否则 `supplement` | 决定表单问什么 |
| `--poc` | 文件路径或通配符 | 无 | `fill` 模式必需；支持 `~` 展开与 `*` |
| `--out` | HTML 路径 | 系统临时目录下的 `poc-form-v3-<项目>-<日期>.html` | 输出位置 |

**意图的默认值是推导出来的，不是写死的**：`--mode new` 必然是 `new` 意图，而填充已有项目
默认是 `supplement`——`progress` 是更窄的动作（只记一轮进展），不该由「没写参数」隐式选中。
要记进展就明确写 `--intent progress`。

这个脚本是**薄封装**：表单的生成逻辑在 `src/form.ts`（打包后 `lib/form.js`），脚本只负责
解析参数、读 YAML、调用 `buildFormHtml`。所以任何表单行为的改动都只改 `src/form.ts`，
两处不能各自演化。若 `lib/form.js` 不存在（未构建），脚本会直接报错并提示先 `npm run build`，
不会降级到任何旧实现。

## 表单填什么

按 v3 分组，和台账结构一致：

| 区块 | 字段 |
|---|---|
| 身份 | 项目名称、体系、主业公司、部门、金额（万元）、项目类型、阶段、状态、进入阶段日期、负责人、销售、客户技术责任人、业务决策人 |
| G0 | 客户为什么测、我们为什么测、决策链、测后客户决策、竞争对手（客户技术责任人算第五条必填） |
| 计划（G1/G2） | 客户痛点、期望认可、成功指标（2–3）、验证场景（3–5）、我方赢点、风险（≤3）、G1 结论、G2 Ready |
| 进展（核心） | 日期、类型、**这一次什么变了**、目标、推进的场景/指标、实际、完成度、证据（标题+链接+类型）、客户同步对象/反馈/认可、G3-1、G3-2、下一步（目标/负责人/截止） |
| 结论 | 目标达成、客户认可、我方证据、证明了什么、客户认可了什么、下一步业务动作、Next Milestone（含负责人/截止/状态）、总体结论 |

**进展是追加的，不是覆盖的。** 组员填的是一条新进展，提交时追加到 `progress[]` 末尾，
不改历史条目——这是 v3 的核心约束。表单里「已有进展」是只读的，就是为此。

## 表单内置功能

| 功能 | 说明 |
|---|---|
| 自动保存草稿 | 停止输入约 0.6 秒后写入 localStorage；另有 30 秒定时保存与关闭页面前保存 |
| 草稿恢复 | 重新打开自动恢复上次未提交内容，顶部提示「已恢复上次未提交的草稿」 |
| 清空草稿 | 顶部【清空草稿】按钮，确认后清掉本机草稿并重载 |
| 项目快照条 | 横幅下方的五个事实格：Gate 0 五必填进度、G0 评审结论、方案（指标/场景数）、进展（轮数+最近日期）、金额。只读 |
| 还需要补 | 快照下方的待办提示条：进入阶段日期缺失、G0 缺口、指标/场景数量不合规。无可补项时不显示 |
| 只读上下文 | 折叠展示台账已有内容：已完成的立项内容（G0 原文）、方案详情（指标/场景/风险明细）、基本信息。只读，点开查看 |
| 已有进展 | 最近若干条进展的时间线（默认展开），让组员知道上一轮报了什么、这一轮该怎么接 |
| 下载变更集 | 底部【下载变更集 (.json)】→ `poc-changes-<日期>.json` |
| 生成回传文件 | 底部【生成回传文件 (.html)】→ `poc-return-<日期>.html`，一个文件即可发回 |
| 预览变更集 | 底部【预览变更集】，在页面上直接看将交回的 JSON |

存储键由**项目编号**派生（不是时间戳），所以同一个项目的表单重新生成后仍能找到旧草稿。

## 导出时先选意图

导出对话框第一步是**这次要做什么**，它决定表单问什么（GUI 与脚本的 `--intent` 是同一件事）：

| 意图 | 表单内容 | 什么时候用 |
|---|---|---|
| **新建项目**（`new`） | 身份 + G0 五必填 | 项目还没进台账 |
| **补充信息**（`supplement`） | 当前阶段该填的，更早阶段作为只读上下文展示 | 某个阶段的内容要补全 |
| **记录进展**（`progress`） | 只展开「已有进展 + 这一轮进展 + 下一步」，一屏 | 每周例行同步 |

批量导出时可以**按阶段筛选**（G0 30 · G1 0 …），给「所有 G0 项目」发一份表单。

## 回传有两种方式，优先用 HTML

组员填完，点底部任一按钮都能交回，**两者内容等价**（都是同一份 `changes[]` 变更集）：

1. **【生成回传文件 (.html)】→ `poc-return-<日期>.html`**（推荐）
   直接把这一个 `.html` 文件通过企业微信发回给发起人。发起人双击就能在浏览器里看到组员填了什么，
   不需要任何额外工具；DSH 侧用 `readReturnDocument` 解析同一个文件里的数据块。
   **好处是不用再单独下载第二个文件**——组员手上收到的那个表单文件本身是空白的，
   填完不会自动变，所以必须生成这份回传副本。

2. **【下载变更集 (.json)】→ `poc-changes-<日期>.json`**
   把下载的 `.json` 同样发回。更小、更严格，适合机器处理；缺点是发起人得用编辑器或
   DSH 才能看懂内容。

## 交给组员时要说清

1. **怎么打开**：双击 HTML，用浏览器打开
2. **填哪些**：只有标了 `*` 的必填项和当前阶段的区块；折叠的「只读」区块是台账已有信息，不用重填
3. **不用怕丢**：自动保存，关掉再打开还在
4. **填完怎么给你**：点【生成回传文件 (.html)】，把那个 `.html` 用企业微信发回；
   或者点【下载变更集 (.json)】把 `.json` 发回。**优先发 HTML**——双击就能看
5. **填不全没关系**：留空的会被标出来（「还需要补」条），提交时统一校验

## 注意

- 生成的文件只在本地（`/tmp` 或指定位置），**不会自动发给任何人**；需要你自己发给组员。
- 组员交回的可以是 `.html` 或 `.json`。`.json` 更严格，不容易被手改坏，而且提交前要经过校验；
  HTML 回传文件里的数据块是**只读快照**（`<script type="application/json">` 里的变更集），
  DSH 只读取、不执行——它不会被当成网页脚本运行。
- 不要用旧版 `poc_form.py`：它产出 v1 字段，台账读不了。
